1. Main objective

Build a complete, professional, mobile-first coding studio application named Code0 in the current Google AI Studio Build workspace.

Code0 must let me use my Android phone to create and manage coding projects, browse and edit source files, connect to GitHub, download repositories, use AI to understand and modify code, review changes before applying them, run available tests, and build Android applications.

This is a real application-development project, not a request for a mockup, landing page, prototype, or collection of nonfunctional screens.

Essential requirements:

- Build the actual application and its supporting source files.

13. CRITICAL FEATURE: AI Change Review, Apply, and Reject

This is one of the most important features in Code0. Implement it as a core workflow, not as a decorative popup.

The AI must never automatically overwrite original project files. The user decides when proposed changes become actual project changes.

Stage A — Prepare changes separately

When the user asks AI to edit a file or implement a feature, prepare the proposed changes separately from the real project.

Keep original project files untouched while the AI is working.

Identify:

- New files.
- Modified files.
- Renamed files.
- Deleted files.
- Changed configuration and dependency files.
- Available validation results.
- Unresolved errors and warnings.

Stage B — Show a completion popup

When AI finishes preparing changes, display a clear notification or popup:

AI changes are ready for review.

Show the task description, number of affected files, and whether validation passed, failed, or could not be run.

Provide these actions:

- Review Changes
- Apply Changes
- Reject Changes

The user must also be able to open proposals from a persistent Pending Changes section after dismissing the popup.

Stage C — Review individual files

Provide a dedicated change-review screen.

For each affected file, show:

- File path.
- Change type.
- Added lines.
- Removed lines.
- Before-and-after comparison.
- Relevant error or test information where available.

Use familiar diff colours and symbols, but never rely on colour alone.

Let users review each file and exclude individual file changes where technically safe.

Clearly identify dependency changes and potentially destructive operations.

Do not label tests as passing if they were not executed.

Stage D — Apply approved changes

When the user taps Apply Changes, update the actual project files with the approved proposal.

Before applying:

- Check that the proposal still matches the current project state.
- Detect files changed since the proposal was created.
- Identify conflicts before modifying files.
- Prepare necessary temporary files.
- Preserve sufficient recovery information.
- Use a controlled transaction or equivalent safe sequence for multi-file changes.
- Verify the expected files were updated.

New files must be created only when approved. Renames and deletions must occur only when explicitly approved.

Report partial failures honestly. Recover from interrupted operations where feasible.

If a file changed after AI prepared its proposal, never silently overwrite the newer version. Show the conflict and allow the user to review, merge, or regenerate the proposal.

Stage E — Reject changes

When the user selects Reject Changes:

- Discard the pending proposal.
- Leave original project files unchanged.
- Remove temporary proposal data when safe.
- Update the pending-changes list.
- Do not create a Git commit.
- Do not push anything to GitHub.

If the user rejects only selected file changes, preserve the remaining proposal for review when safe.

Stage F — Undo and recovery

After applying approved changes, offer undo where technically possible.

Store only the recovery information necessary to reverse the operation. Do not create a full duplicate of the project for every AI task.

Clearly indicate when a change cannot be safely undone.

Never silently apply AI changes, silently discard user edits, or automatically push AI-generated changes to GitHub.
